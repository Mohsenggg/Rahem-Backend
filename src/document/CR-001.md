## Task 1 — User Profile: Expose Node ID

**Type / Priority:** Feature / Medium

**Current behavior**
`AuthService.userToUserDto()` resolves `nodeName` by querying `NodeRepo.findFirstByUserIdAndIsDeletedFalse()` but does not return `nodeId`. The frontend `LoginResponse` interface has no `nodeId` field and the sidebar shows no node ID.

**Expected behavior**
After login/register, the `user` object includes the linked `nodeId` (business key from `node.nodeId`, not the DB `id`). The sidebar displays it.

**Root cause / analysis**
- `UserDataDto` fields: `id`, `username`, `email`, `fullName`, `nodeName`, `roles` — no `nodeId`.
- `AuthService.userToUserDto()` already fetches the `Node` to get the name; `node.getNodeId()` is available at that same point.
- Frontend `LoginResponse.user` mirrors this gap.

**Implementation approach**
1. Add `Long nodeId` to `UserDataDto`.
2. In `AuthService.userToUserDto()`, capture the resolved `Node` and set `dto.setNodeId(node.getNodeId())`.
3. Add `nodeId?: number` to the `LoginResponse.user` interface in the frontend.
4. Display `nodeId` in the sidebar user section of `home-rahem.component.html`.

**Affected files/components**
- `UserDataDto.java`
- `AuthService.java` — `userToUserDto()`
- `LoginResponse.ts`
- `home-rahem.component.html` — sidebar user section

**Acceptance criteria**
- Login and register responses include `nodeId` when a node is linked to the user.
- `nodeId` is absent/null when no linked node exists.
- Node ID is stored in `UserProfile` (`user_profile` table).

**Dependencies:** None

### Implementation Notes & Completion Summary

- **Status:** Completed
- **What was changed:**
  - `UserProfile.java`: Added `@Column(name = "node_id") private Long nodeId;` to persist the linked tree node ID in the `user_profile` table.
  - `UserDataDto.java`: Added `private Long nodeId;` to expose `nodeId` in user authentication DTOs.
  - `AuthService.java`:
    - Updated `register()` to save `nodeId` on `UserProfile` from the validated invitation node (`node.getNodeId()`).
    - Updated `userToUserDto()` to populate `nodeId` on `UserDataDto` from `node.getNodeId()`.
  - `RegistrationService.java`: Updated `approveRegistration()` to set `nodeId` on `UserProfile` when approving registrations.
  - `AuthServiceTest.java`: Added unit tests verifying `nodeId` persistence in `UserProfile` during registration and DTO mapping during login.
  - Database (`rahemDB`): Added `node_id` column to `user_profile` and backfilled all existing user profiles with their corresponding `node.node_id`.
- **Implementation Details & Decisions:**
  - `nodeId` stores the business node ID (from `node.getNodeId()`), matching the ID used throughout tree operations.
  - If a user has no linked tree node, `nodeId` remains `null`.

## Task 2 — CRITICAL: Tree Positioning Bug (External-Parent Node)

**Type / Priority:** Bug / Critical

**Current behavior**
A node has `motherId` pointing to a regular in-tree node and `fatherId` pointing to a ghost/external node (`level = -1`, `isExternal = true`). When the mother is clicked, her children appear at the top of the page instead of under her.

**Expected behavior**
Children render in the correct vertical row (in-tree parent level + 1) regardless of whether the other parent is external.

**Root cause / analysis**
The bug is in `NodeService.createNode()`:

```java
Long primaryParentId = request.getFatherId() != null ? request.getFatherId() : request.getMotherId();
Node primaryParent = nodeRepo.findByNodeIdAndIsDeletedFalse(primaryParentId).orElseThrow(...);
node.setLevel(primaryParent.getLevel() + 1);
```

When both parents are provided, `fatherId` is always used first. If the father is a ghost node (`level = -1`), the child gets `level = 0`. Level 0 triggers `addL0NodeLayout()` in `TreeLayoutService`, which always renders at `topSpaceY = windowHeight * 0.05` (the very top).

Secondary: `TreeService.getNodesWithTreeId()` correctly filters out external nodes before sending to the frontend. The child is still found via `motherId` in `TreeStructureService.getChildren()`. The positioning error is entirely a stored-level issue from creation time.

**Implementation approach**
In `NodeService.createNode()`, when both parents are provided, resolve the non-external parent for level calculation:

```java
Node primaryParent;
if (request.getFatherId() != null && request.getMotherId() != null) {
    Node father = nodeRepo.findByNodeIdAndIsDeletedFalse(request.getFatherId()).orElseThrow(...);
    Node mother = nodeRepo.findByNodeIdAndIsDeletedFalse(request.getMotherId()).orElseThrow(...);
    // Prefer the in-tree parent for level assignment
    primaryParent = Boolean.TRUE.equals(father.getIsExternal()) ? mother : father;
} else {
    Long id = request.getFatherId() != null ? request.getFatherId() : request.getMotherId();
    primaryParent = nodeRepo.findByNodeIdAndIsDeletedFalse(id).orElseThrow(...);
}
```

All other logic (same-tree validation, node save) remains unchanged.

> **Note:** Nodes already stored with `level = 0` due to this bug need a one-time manual DB correction.

**Affected files/components**
- `NodeService.java` — `createNode()`
- DB: manual data fix for affected nodes

**Acceptance criteria**
- A child added with one external parent gets `level = inTreeParent.level + 1`.
- Clicking the in-tree parent shows children at the correct vertical position.
- Normal two-in-tree-parent relationships are unaffected.
- External-parent-only scenario (single parent, external) is unaffected.

**Dependencies:** None

### Implementation Notes & Completion Summary

- **Status:** Completed
- **What was changed:**
  - In `NodeService.createNode()`: When both `fatherId` and `motherId` are provided, both father and mother entities are fetched and validated for tree consistency. `primaryParent` is assigned using `Boolean.TRUE.equals(father.getIsExternal()) ? mother : father`, ensuring the in-tree parent is prioritized for `level` calculation (`primaryParent.getLevel() + 1`) and tree association.
  - In `NodeServiceTest.java`: Added unit tests verifying level calculation when father is external (`isExternal = true`, `level = -1`) with an in-tree mother, and when mother is external with an in-tree father.
- **Implementation Details & Decisions:**
  - Fallback to `mother` occurs whenever `father.getIsExternal()` is true, preventing ghost nodes (`level = -1`) from resetting child node levels to `0`.
  - Same-tree validation is preserved across both parents.
- **Considerations for Remaining Tasks:**
  - Historical node records previously inserted into persistent databases with `level = 0` due to this bug may need a one-time DB level update if present.

## Task 3 — Registration Birth Date UX (Year to Month to Day)

**Type / Priority:** UX / Low-Medium

**Current behavior**
The birth date field is a plain `<input type="date">` (register.component.html, line 353). On mobile the native calendar picker is difficult to navigate for users selecting a birth year decades in the past.

**Expected behavior**
Three cascading dropdowns in order: Year, Month, Day. Day options update based on selected year and month.

**Root cause / analysis**
- Single `formControlName="birthDate"` bound to a date string.
- No external date-picker library is in use. `pastDateValidator` checks only the final assembled date.
- The change is entirely in the component and template; no backend change needed.

**Implementation approach**
1. In `register.component.ts`, replace `birthDate: ['', [...]]` with three controls: `birthYear`, `birthMonth`, `birthDay`. Add a private `assembleBirthDate(): string` method returning `YYYY-MM-DD`. Apply `pastDateValidator` as a form-group validator or inline on submit.
2. Populate year options (current year down to 1900), month options (1-12 with Arabic month names), and day options (1 to N where N depends on selected year + month).
3. In `register.component.html`, replace the date input block (lines 350-364) with three `<select>` elements using the existing `form-control` class. Order: Year, Month, Day.
4. On submit, call `assembleBirthDate()` and map the result to `birthDate` in `RegisterRequest`.

**Affected files/components**
- `register.component.ts` — form definition, date assembly, day-count logic
- `register.component.html` — birth date section (lines 350-364)

**Acceptance criteria**
- Year dropdown appears first, then Month, then Day.
- Day count is correct for all months including Feb 28/29.
- Validation blocks future dates.
- Backend receives a valid `YYYY-MM-DD` string.
- No new npm library added.

**Dependencies:** None

## Task 4 — Dynamic Statistics Post (Home Page)

**Type / Priority:** Feature / Medium

**Current behavior**
`home-rahem.component.html` has a static `status-skeleton` placeholder (lines 49-55). The tree card `nodeCount()` is loaded from `MockTreeDataService`, not the real API, and excludes external nodes and member counts.

**Expected behavior**
The statistics section shows live data:
- Total tree nodes (all non-deleted, including external)
- Joined members (count of UserProfile records)
- External nodes (secondary stat)

**Root cause / analysis**
- `HomeRahemComponent` uses `{ provide: TreeDataService, useClass: MockTreeDataService }` — bypasses the real API.
- No stats endpoint exists on the backend.
- `TreeService.getNodesWithTreeId()` filters out external nodes, so it cannot supply `totalNodes`.
- `UserProfileRepository` has no count query.

**Implementation approach**

Backend:
1. Create `TreeStatsDto.java` with fields: `Long totalNodes`, `Long joinedMembers`, `Long externalNodes`.
2. Add to `NodeRepo`:
   - `long countByTreeTreeIdAndIsDeletedFalse(Long treeId)` (total, including external)
   - `long countByTreeTreeIdAndIsExternalTrueAndIsDeletedFalse(Long treeId)` (external only)
3. Add `long count()` or a named query to `UserProfileRepository` (built-in JPA `count()` is sufficient).
4. Add `getTreeStats(Long treeId)` to `TreeService` that calls the above and returns `TreeStatsDto`.
5. Add `GET /api/trees/{treeId}/stats` to `TreeController`.

Frontend:
1. Add `getTreeStats(treeId: number): Observable<TreeStats>` to `ApiTreeDataService`.
2. In `HomeRahemComponent`: switch the provider from `MockTreeDataService` to `ApiTreeDataService`, call `getTreeStats(1)` on init, populate signals.
3. Replace the `status-skeleton` section with real stat cards bound to the signals.

**Affected files/components**
- `NodeRepo.java` — add two count queries
- `UserProfileRepository.java` — confirm or add count support
- `TreeStatsDto.java` — new DTO
- `TreeService.java` — new `getTreeStats()` method
- `TreeController.java` — new `GET /{treeId}/stats` endpoint
- `ApiTreeDataService.ts` — add `getTreeStats()`
- `home-rahem.component.ts` — switch provider, call stats, populate signals
- `home-rahem.component.html` — replace skeleton with stat cards

**Acceptance criteria**
- `GET /api/trees/1/stats` returns `{ totalNodes, joinedMembers, externalNodes }`.
- Home page displays real values, not skeleton.
- Values reflect actual DB state.

**Dependencies:** None

## Task 5 — FAB Selection Mode Indicator

**Type / Priority:** UX / Low

**Current behavior**
After tapping any FAB action (Add Member, Update Member, Create Invitation), the FAB closes with no visible cue that the user must tap a node to continue. `isEditMode` and `isInvitationMode` signals are set but the panel only renders after a node is selected.

**Expected behavior**
A hint bar appears below the header telling the user to select a node. It uses the same pattern as the partner selection hint already present in the codebase.

**Root cause / analysis**
- `openAddChildPanel()` sets `isEditMode = true`, `selectedNodeToEdit = null`.
- `openUpdatePanel()` sets `isEditMode = true`, `selectedNodeToEdit = null`.
- `toggleInvitationMode()` sets `isInvitationMode = true`, `selectedNodeToEdit = null`.
- `view-tree.component.html` lines 31-35 contain a commented-out `.partner-selection-hint` block for `isSelectingPartner`. The CSS class and concept already exist.

**Implementation approach**
Add one computed signal in `view-tree.component.ts`:

```ts
isAwaitingNodeSelection = computed(() =>
  (this.isEditMode() || this.isInvitationMode()) && !this.selectedNodeToEdit()
);
```

Uncomment and extend the existing hint block in `view-tree.component.html`:

```html
<div class="partner-selection-hint"
     *ngIf="isAwaitingNodeSelection() || isSelectingPartner()">
  <svg lucideHandshake [size]="15" [strokeWidth]="2"></svg>
  <span>{{ isSelectingPartner() ? 'اختر شريكاً من الشجرة' : 'اختر عضواً من الشجرة' }}</span>
</div>
```

Reuse the existing `.partner-selection-hint` CSS rule. No new styles needed.

**Affected files/components**
- `view-tree.component.ts` — add `isAwaitingNodeSelection` computed signal
- `view-tree.component.html` — uncomment and extend hint block
- `view-tree.component.css` — optional visual tweaks only

**Acceptance criteria**
- Hint appears after any FAB action when no node is selected.
- Hint disappears when a node is tapped (panel opens).
- Hint disappears on cancel.
- Partner selection hint still works.

**Dependencies:** None

## Task 6 — CRITICAL: Existing Children Not Linked to New Partner

**Type / Priority:** Bug / Critical

**Current behavior**
When a partner is added to a node that already has children, those children's `motherId` or `fatherId` (whichever corresponds to the new partner's gender) remain `null`.

**Expected behavior**
To be confirmed — see analysis.

**Root cause / analysis**
- `Node.fatherId` / `Node.motherId` are plain columns with no cascade.
- `NodePartnerService.addPartner()` only inserts into `node_partner`; it never touches child nodes.
- No existing logic propagates partner assignment to children.

Business rule table:

| Scenario | Auto-assign safe? |
|---|---|
| Node A (MALE), children with motherId = null. Partner B (FEMALE) added. | Conditionally safe — B is the only candidate. |
| Node A (MALE), children with motherId = X (different node). Partner B (FEMALE) added. | Unsafe — existing mother must not be overwritten. |
| Node A (FEMALE), children with fatherId = null. Partner B (MALE) added. | Conditionally safe — symmetric. |

> **Business clarification required:** Should the system auto-assign the new partner as the missing parent for children where the slot is null? Or must this always be an explicit user action?

**Recommended approach (pending clarification):** Explicit user confirmation after partner creation.

1. After creating the `NodePartner`, compute `unlinkedChildrenCount` — the count of node A's children where the new partner's gender slot is null — and return it in `NodePartnerDto`.
2. If `unlinkedChildrenCount > 0`, the frontend edit panel shows a prompt asking the user to assign the new partner as the missing parent.
3. On confirmation, call `POST /api/nodes/{nodeId}/partners/{partnershipId}/assign-children` which sets `motherId` or `fatherId` only on children where the slot is currently null (never overwrites existing values).

**Affected files/components** (if explicit-assignment approach is approved)
- `NodePartnerDto.java` — add `unlinkedChildrenCount`
- `NodePartnerService.java` — `addPartner()`: compute count
- `NodeRepo.java` — add query for children with null parent slot
- `NodePartnerController.java` — add `POST /{partnershipId}/assign-children`
- `NodeService.java` — new `assignPartnerToChildren()` method
- `edit-panel.component.ts` / `.html` — show assignment prompt
- `ApiTreeDataService.ts` — add `assignPartnerToChildren()` call

**Acceptance criteria** (post-clarification)
- Children with a filled parent slot are never overwritten.
- User is informed when eligible children exist and can choose to assign.
- After confirmation, children's `motherId`/`fatherId` are correctly set.
- Tree re-renders with updated parentage without a full page reload.

**Dependencies:** Business rule must be confirmed before implementation.
